# 10 — Architecture

## Shape

`dusk` is one Zig package. A consumer adds it as a dependency and imports the
module `dusk`.

```
build.zig
build.zig.zon          one dependency: the pinned Vulkan headers
src/
  root.zig             the module root; re-exports the public surface
  vulkan.zig           GENERATED by translate-c; not hand-edited
  vk.zig               hand-written dispatch layer over vulkan.zig
  spirv/               SPIR-V binary parser, validator, reflection
  api/                 the WebGPU front end, generated from dawn.json
  core/                object model, errors, futures, refcounting policy
  engine/              instance, adapter, device, queue, resources
  command/             command stream, encoders, passes, validation
  memory/              VMA wrapper plus the WebGPU-specific layers
  pipeline/            shader modules, pipelines, caches
  platform/            loader, threads, process, window surfaces
tools/
  gen_api.zig          comptime generator: dawn.json -> src/api
  gen_dispatch.zig     comptime generator: headers -> src/vk.zig table
docs/
test/                  the test tree
examples/              runnable, headless-capable acceptance programs
```

`src/vulkan.zig` is generated. It is checked in so a consumer does not need a
C toolchain to build, and `build.zig` regenerates it when the pinned commit
changes. `tools/` holds the generators and nothing else; each is a Zig program,
not a shell script.

## Module boundaries

Each module owns its own data and is reached through functions. A module never
reaches into another's fields.

| Module | Owns | Never does |
| --- | --- | --- |
| `vulkan` | The generated C bindings. | Anything but re-exporting them. |
| `vk` | Loading `libvulkan`, the three-tier dispatch table, `VkResult` to Zig error mapping. | Call a Vulkan entry point directly; the table is the only door. |
| `spirv` | Parsing a SPIR-V binary, validating it, reflecting it. | Touch Vulkan types. |
| `api` | The public WebGPU surface: handles, descriptors, enums. | Hold engine state. |
| `core` | Object lifetime policy, error sets, futures, string views. | Know what a texture is. |
| `engine` | Instance, adapter, device, queue, buffers, textures, bind groups. | Encode commands. |
| `command` | The command stream, encoders, passes, pass-level validation. | Touch Vulkan. |
| `memory` | VMA, the size tracker, serial reclamation, per-resource allocations. | Know which resource it is allocating for, only as an allocation record. |
| `pipeline` | Shader modules, render and compute pipelines, the cache. | Execute. |
| `platform` | Threads, the loader shim, surface creation. | Call into `engine`. |

The dependency direction is strictly downward:

```
api  ->  core
engine -> core, command, memory, pipeline
command -> core, memory
pipeline -> core, spirv, memory
vk -> vulkan
platform -> core
```

`command` does not import `vk`. It records an intent; `engine` replays it into
`vk`. That split is what keeps the front end testable without a GPU and is the
same split Dawn makes at `CommandBufferVk.cpp:1132`.

## Object model

Every WebGPU object is a handle. Internally each is a pointer to a refcounted
struct allocated from the device's arena.

```zig
pub const Device = struct {
    arena: std.heap.ArenaAllocator,
    // ...
};

pub fn createBuffer(dev: *Device, desc: BufferDescriptor) Error!Buffer { ... }
pub fn destroyBuffer(dev: *Device, buf: Buffer) void { ... }
```

A handle carries no state of its own, so copying one is free and cannot
double-free. The last reference releases into the arena, which is reclaimed when
the device is destroyed. There is no per-object free, and therefore no use-after-
free: a stale handle reads memory the arena still owns, which the debug layer
reports as a validation error rather than as undefined behaviour.

This is the deliberate departure from Dawn's intrusive `Ref<T>` with a two-bit
payload refcount (`docs/02-dawn-design.md` §4.1). The trade is documented in
`docs/30-port-design.md`.

## Threading

One device mutex, one serial timeline, one worker pool. That is Dawn's model and
it is correct: WebGPU's ordering guarantees are a serial order.

- The **device mutex** guards every public entry point. Public API calls are
  never blocking; they enqueue.
- The **serial timeline** is a monotonic counter. Work submitted at serial *n*
  completes before work submitted at serial *n+1*.
- The **worker pool** runs exactly two jobs: SPIR-V validation at shader-module
  creation, and pipeline creation when the caller asked for it asynchronously.

Nothing else starts a thread. A fence is polled from the device tick, never from
a thread of its own.

## The command path

A consumer records into an encoder. The encoder appends typed commands into a
block arena (`command`). At submit, the device replays that stream into Vulkan
entry points (`engine` → `vk`).

This is Dawn's architecture verbatim: a 38-tag command stream in
`Commands.h:55-94`, replayed by `CommandBufferVk::RecordCommands`. Keeping it
buys three things — the front end is testable with no GPU, validation can run
against recorded state rather than live objects, and the Vulkan backend stays a
leaf module.

---

## Shaders

The port takes **SPIR-V** on native targets, the same shape as Dawn's
`shader source SPIRV`. A WGSL front end is out of scope.

The flow is: SPIR-V bytes → `spirv.validate` → `spirv.reflect` → a
`vkCreateShaderModule` on the caller's own words.

Dawn cannot do this: it round-trips through Tint and regenerates
(`docs/02-dawn-design.md` §4.9). That round trip is the single largest thing the
port does not carry, and it buys back 753,961 lines of `src/tint`.

---

## Compatibility mode

A device is in compatibility mode when the `core features and limits` feature is
absent. That single rule drives limit selection and every per-object compat
check, exactly as Dawn does it (`docs/02-dawn-design.md` §5). It is a runtime
derivation, never a build flag.
